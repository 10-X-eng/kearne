# Solid Modeling

- **Status:** Proposed
- **Requirement prefix:** `MOD`
- **Depends on:** [Persistent topology](../foundations/04-persistent-topology.md), [sketcher](02-sketcher.md), [evaluation](../foundations/03-evaluation-and-jobs.md), [numerics](../foundations/05-units-expressions-numerics.md)
- **Unblocks:** MVP, assemblies, drawings, simulation

## 1. Purpose

Define a uniform native feature contract and the first set of semantic solid operations. Feature count grows through reusable validation/evaluation/topology infrastructure rather than bespoke UI-to-OCCT paths.

## 2. Feature descriptor

Every feature type registers:

```text
stable type and schema version
parameter schema with dimensions/defaults
allowed input/reference kinds
declared output slots
semantic validator
dependency extractor
evaluator and fingerprint
topology naming publisher
diagnostic mapper
edit-support matrix
migration handler
command/UI metadata
test-domain generator
```

### MOD-001 — One evaluator contract

Native and supported plugin features implement the same snapshot-to-immutable-result port. They do not directly update bodies, render scenes, files, or UI state.

### MOD-002 — Explicit body scope

Every solid-producing operation declares whether it creates a body and which bodies it targets or consumes. “Automatically use whatever body is active” is UI command construction, not persisted semantics.

### MOD-003 — Validation layers

Schema/reference/unit errors reject a command. Kernel feasibility errors produce a committed feature with failed evaluation and structured diagnostics. Feature-specific validation is reused by GUI, Python, AI, and replay.

## 3. MVP feature semantics

### Extrude

Inputs: one or more closed sketch profile-loop references, direction derived from sketch frame or explicit vector, extent, operation, explicit target bodies.

MVP extents: one-sided distance and symmetric distance. Operations: new body, additive, subtractive, intersection. Draft, thin, up-to-face, and two-sided unequal extents follow later.

Topology contract includes start/end cap, faces generated by stable profile entities, and modified target topology.

### Revolve

Inputs: profile loops, semantic sketch/datum axis, signed angle, operation, explicit targets. MVP rejects self-intersecting sweeps and axes that produce unsupported degeneracy with actionable diagnostics.

### Boolean

Inputs: explicit ordered target set and tool set. Operations: union, subtract, intersection. “Keep tools” is explicit. Output/body identity rules for multiple solids must be resolved under `DOC-OPEN-003` before implementation.

### Fillet and chamfer

Inputs: explicit edge topology references and dimensional parameters. MVP supports constant-radius fillet and equal-distance chamfer. Variable radius, setback, face-face, and partial-edge variants are later schemas rather than overloaded magic fields.

### Hole

MVP supports simple and standards-backed clearance holes with semantic placement, diameter/fit record, termination, and cosmetic-thread metadata where relevant. Standard database identity/version is persisted; resolved dimensions are retained so database updates do not silently alter old designs.

### Patterns

Linear and circular feature patterns reference a source feature/result, stable member keys, count, spacing/angle, direction/axis, suppression set, and target scope. Count changes preserve unaffected member identity.

## 4. Evaluation rules

### MOD-004 — Kernel pre/post validation

The OCCT adapter validates finite/range-safe inputs before invocation and validates output shape status, expected dimensionality, body count policy, bounds, and topology publication before success.

### MOD-005 — No automatic repair without semantics

Kernel healing that changes feature meaning, removes topology, or changes tolerance beyond policy is never silently applied to a native result. Safe normalization steps are versioned as part of the evaluator fingerprint.

### MOD-006 — Diagnostics preserve context

Kernel exceptions/statuses map to stable feature diagnostics with semantic input references and evidence-backed repairs when available. Raw kernel text may be attached as developer detail but is not the stable API.

### MOD-007 — Cancellation containment

Feature evaluation runs through the scheduler and geometry-worker policy. An uninterruptible boolean or fillet cannot block UI or publish partial body/topology state.

## 5. Feature ordering and dependencies

Feature history is a display projection of body-tip and explicit dependencies. Reordering is a command that validates dependency legality and changes explicit body/result bindings. It is not a vector shuffle with implicit “previous feature” behavior.

Suppression retains the feature entity and identity but removes its current contribution according to feature-specific pass-through rules. Downstream references are re-evaluated and may become broken.

## 6. Direct modeling and imported bodies

Later move/offset/delete/replace-face operations are ordinary semantic features whose inputs reference imported or native topology. Feature recognition produces proposals; accepting recognition creates native features with explicit confidence/provenance and never discards the original imported source artifact automatically.

## 7. Verification strategy

Every feature participates in one generated conformance harness that verifies:

- schema and dimensional validation;
- evaluator determinism classification and artifact integrity;
- body-scope invariants;
- topology publication completeness and edit matrix;
- transform and unit metamorphisms where mathematically applicable;
- cancellation/worker-death containment;
- save/reload/replay equivalence;
- command parity across adapters;
- invalid parameter domains fail without crashes or non-finite outputs.

Geometry oracles are layered:

1. shape validity and expected dimensionality;
2. analytic/property relations such as extruded volume = profile area × distance;
3. containment/intersection and mass-property invariants;
4. topology ancestry properties;
5. differential comparison when an independent construction or implementation exists;
6. bounded curated kernel regressions.

BREP byte identity and a growing catalog of hand-authored part files are not the primary strategy.

## 8. Acceptance scenarios

- Parameterized mounting plate with patterned clearance holes and fillets survives dimensional edits.
- Revolved shaft retains cylindrical/planar semantic selections after length/diameter changes.
- Boolean tool movement transitions success -> no intersection -> success without losing feature intent.
- Oversized fillet fails, reports affected edge and approximate remediation when available, then recovers after radius edit.
- Pattern count changes preserve source and unaffected member references.

Each scenario runs from the same command log through headless, GUI-smoke, Python, and AI-command adapters as applicable.

## 9. Open decisions

- **MOD-OPEN-001:** Detailed multi-body split/merge and body identity rules.
- **MOD-OPEN-002:** Exact MVP hole termination and standards-data subset.
- **MOD-OPEN-003:** Whether tessellation occurs in the same geometry worker invocation or a separate artifact job.
- **MOD-OPEN-004:** Supported OCCT boolean/fuzzy tolerance policy.
- **MOD-OPEN-005:** Feature reorder UX and semantic limits.

## 10. Definition of done

A native feature is done only when its descriptor, commands, evaluator, topology contract, migrations, generated domains, conformance properties, diagnostics, and headless documentation are complete. A toolbar button and one successful sample shape are insufficient.
